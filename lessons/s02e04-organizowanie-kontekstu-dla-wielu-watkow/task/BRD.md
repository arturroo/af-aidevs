# Business Requirements Document (BRD) - Task: `mailbox`

## 1. Overview
An operative from the resistance infiltrated the communications network and compromised access to an email inbox belonging to an operator of the hostile System. The informant discovered that a defector within the resistance named **Wiktor** (operating from an anonymous address on the `proton.me` domain) has betrayed the resistance and established contact with the System. Wiktor submitted a denunciation exposing our team, our power plant operations, and our ongoing plans.

The objective of this task is to systematically inspect and search the operator's mailbox via its specialized API (`zmail`) to uncover three vital pieces of intelligence:
1. **`date`**: The scheduled attack date when the security department plans to strike our power plant (strictly in `YYYY-MM-DD` format).
2. **`password`**: The password for the internal employee system, which is believed to still reside within the mailbox history.
3. **`confirmation_code`**: The confirmation code from the security ticket generated by the security department (strict format: `SEC-` followed by 28 characters, totaling exactly 32 characters).

A critical operational challenge is that the target mailbox is **live and actively used**; new messages, updates, and ticket notifications may arrive asynchronously in real-time during execution. The autonomous agent must account for this by employing iterative search strategies and polling/retrying if a required field is not immediately found.

---

## 2. Business Objectives
- **Targeted Intelligence Extraction**: Accurately discover and extract all three required fields: attack `date`, employee system `password`, and security ticket `confirmation_code`.
- **Active Mailbox Traversal**: Adapt to dynamic inbox state changes where critical correspondence (such as newly opened security tickets) may arrive after initial exploration.
- **Two-Stage Retrieval Workflow**: Leverage the Zmail search engine to filter and retrieve message metadata and identifiers, followed by fetching full email bodies for candidate messages.
- **Iterative Verification Loop**: Submit discovered credentials and telemetry to Centrala via the verification endpoint, consuming hub feedback to identify missing or rejected values until full validation is achieved.
- **Zero-Trust Safety & Sanitization (Model Armor)**: Screen all untrusted external email contents retrieved from the operator mailbox via Model Armor (`af_aidevs.model_armor`) to eliminate indirect prompt injections, adversarial exploits, and jailbreak vectors before LLM context ingestion.
- **Flag Capture**: Secure and record the completion course flag (`{FLG:...}`) upon full acceptance of the response payload.

---

## 3. Data & API Requirements

### 3.1 Zmail Mailbox API
Access to the compromised operator inbox is provided via the Zmail JSON API:
- **Endpoint**: `$AIDEVS_API_ZMAIL`
- **Method**: `POST`
- **Headers**: `Content-Type: application/json`
- **Base Request Structure**:
  ```json
  {
    "apikey": "$AIDEVS_API_KEY",
    "action": "<action_name>",
    "page": 1
  }
  ```

#### Key Actions & Capabilities
1. **API Discovery (`action: "help"`)**:
   - Querying the `help` action returns the full specification of supported API actions, optional filtering arguments, and parameter types.
2. **Inbox Inspection (`action: "getInbox"`)**:
   - Fetches the standard inbox message listing (subject, sender, timestamp, message ID) with pagination support.
3. **Gmail-Style Search**:
   - The search engine supports advanced Gmail-compatible operators, including:
     - `from:<address/domain>` (e.g., `from:proton.me`)
     - `to:<address>`
     - `subject:<term>`
     - Logical operators: `AND`, `OR`
     - Keyword searches across message headers and topics
4. **Full Message Retrieval**:
   - Fetching complete message text by message ID to read message bodies, extract embedded codes, passwords, and incident logs.

### 3.2 Verification API
Final answers are submitted to the Centrala verification hub:
- **Endpoint**: `$AIDEVS_API_VERIFY`
- **Method**: `POST`
- **Headers**: `Content-Type: application/json`
- **Payload Schema**:
  ```json
  {
    "apikey": "$AIDEVS_API_KEY",
    "task": "mailbox",
    "answer": {
      "password": "<found_password>",
      "date": "YYYY-MM-DD",
      "confirmation_code": "SEC-..."
    }
  }
  ```

### 3.3 Feedback & Verification Mechanics
- **Partial Feedback**: The verification hub inspects the `answer` object and returns actionable feedback indicating which fields are missing, invalid, or incorrectly formatted.
- **Completion Response**: When all three attributes are correct, the hub responds with HTTP 200 and the completion flag `{FLG:...}`.

## 4. Functional Requirements & Extraction Rules

### 4.1 Field Validation Rules
1. **Attack Date (`date`)**:
   - Must match ISO date format: `YYYY-MM-DD` (e.g., `2026-02-28`).
   - Must represent the specific scheduled date of the security department's assault on the power plant.
2. **Employee Password (`password`)**:
   - Plaintext string representing the credential to the employee portal found in historical correspondence.
3. **Ticket Confirmation Code (`confirmation_code`)**:
   - Regex validation: `^SEC-[A-Za-z0-9]{28}$`
   - Must begin with prefix `SEC-` followed by exactly 28 characters (total length: 32 characters).

### 4.2 Dynamic Search & Polling Strategy
- **Initial Broad Search**: Search for correspondence from Wiktor using `from:proton.me` and keywords related to the power plant (`elektrownia`, `atak`, `ruchu oporu`).
- **Credential Search**: Search for system credentials using keywords such as `hasło`, `password`, `dostęp`, `pracownik`, `system`.
- **Security Ticket Search**: Search for security alerts and tickets using terms like `ticket`, `security`, `bezpieczeństwo`, `SEC-`.
- **Live Mailbox Polling**: If the security ticket or the attack confirmation has not yet landed in the inbox, the agent must wait or re-query the search endpoint across successive iterations, as new emails arrive in real-time.

### 4.3 Zero-Trust Security Verification (cr-model-armor & af-aidevs SDK)
- **Untrusted Ingestion Protection**: The compromised operator inbox contains third-party emails from unverified actors (such as Wiktor or system security broadcasts) which may contain indirect prompt injections, phishing, or adversarial extraction instructions.
- **Shared Package Integration**: We strictly use `af_aidevs.model_armor` from the central `af-aidevs` package (published to Artifact Registry / resolved via `uv`).
- **Target Microservice & JWT Auth**: Calls are dispatched to our internal Cloud Run microservice `cr-model-armor` (`$MODEL_ARMOR_URL`). Authentication is handled automatically via Google Cloud JWT / OIDC identity tokens (no manual API tokens required).
- **Verification Hook**: Before passing the body of any retrieved message to the agent's context or parsing tools, the system invokes `await model_armor.verify(text, policy_context="zmail_body", session_id=session_id)`.
- **Sanitization & Quarantining**: If Model Armor flags a message as malicious or non-compliant, the message body is quarantined, an audit alert is streamed to BigQuery telemetry, and the agent continues execution without ingesting unsafe instructions.

## 5. System & Model Constraints
- **Primary LLM**: **Gemini 3.8 Flash** (`gemini-3.8-flash`) on Google Cloud Vertex AI via the modern `google-genai` SDK and `langchain-google-genai`.
- **Thinking Configuration**: Default setting is `thinking_level="low"` (or `types.ThinkingLevel.LOW`) to guarantee fast response latency and minimal token consumption while performing search and extraction tasks.
- **Dual Framework Architecture**: Implementation must support both **LangChain (1.2.15)** and **Google GenAI SDK** via the `--backend` CLI parameter (defaulting to `langchain`).
- **Telemetry & Auditing**: Every tool call, thought, search query, and verification attempt must be streamed to BigQuery dataset `s02e04` using the standardized `X-Session-ID` format (`s02e04_{backend}_{YYYYMMDD_HHMMSS}`).

## 7. Success Criteria
1. Agent initializes and executes `help` action on `$AIDEVS_API_ZMAIL` to discover supported parameters.
2. Agent executes structured searches against the mailbox, identifying relevant emails from Wiktor (`from:proton.me`) and internal operators.
3. Candidate message contents are fetched and verified through Model Armor (`af_aidevs.model_armor`) before LLM analysis to sanitize against indirect prompt injection.
4. Candidate message contents are parsed to extract:
   - Scheduled attack date (`date` in `YYYY-MM-DD` format).
   - Employee password (`password`).
   - Ticket confirmation code (`confirmation_code` matching `SEC-` + 28 characters).
5. If any required information is missing due to asynchronous delivery, the agent autonomously polls or re-queries the mailbox.
6. Answer payload is submitted to `$AIDEVS_API_VERIFY` and successfully validated.
7. The course flag `{FLG:...}` is captured, logged to BigQuery, and saved to `run_notes.txt`.
